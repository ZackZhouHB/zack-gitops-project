What Happened

Earlier today, some teachers were unable to activate their accounts because Amazon SES rewrote the HTTPS activation links generated by our teacher application into insecure HTTP tracking links (awstrack.me). This mixed-content redirect was blocked by modern browsers, leading to blank or error pages when click the link.

Account level enabled “open” and "click" tracking in SES silently turned on link rewriting, and—because no secure, custom redirect domain was configured—the service defaulted to an insecure generic domain.

I had to disable engagement tracking in Virtual Deliverability Manager for a quick fix, moving forward, we will configure a branded HTTPS redirect domain in a dedicated SES configuration set before re-enabling tracking.

Investigation

  1. Initial Report — Several teachers reported that the activation link in their email was not working.
  2. Verifying the Application — The teacher application generated a correct, functional link: https://xxxx.nsw.edu.au/…, confirming the application itself was not at fault.
  3. Analyzing the Email — In the email received, the link had been rewritten to http://cs8fdnj.r.ap-southeast-2.awstrack.me/….
  4. Identifying the Change — awstrack.me is Amazon SES’s default click-tracking domain, used to monitor link clicks.
  5. Pinpointing the Configuration — In configuration set xxxx-ses-config-set, “open” tracking was not enabled, which should not automatically activated link rewriting.

Root Cause Analysis

  • Immediate Cause: Amazon SES automatically rewrote links in the invitation email which proved when saw awstrack.me.
  • Contributing Cause: The rewritten link was insecure (http://) while the destination was secure (https://), triggering mixed-content blocks.
  • Underlying Cause: Engagement tracking was enabled in the account level under AWS SES Virtual Deliverability Manager, even we have a configuration set with event destination for unchecked `open` and `click`. needing a custom, company-branded, secure redirect domain, to prevent SES to fall back to an insecure generic domain.

Resolution (Immediate Fix)

  1. Opened xxxx-ses-config-set in the SES console.
  2. Located the event destination sespoc that enabled tracking.
  3. Verified that tracking for email opens and clicks was not active in the existing event destination.
  4. Turned off engagement tracking in Virtual Deliverability Manager (account level).
  5. Sent a new invitation to confirm the link now pointed directly to the teacher application; activation succeeded.

Status: The system is fully functional.

Custom Redirect Domains (Long-Term)

Why?

  • Brand-aligned URLs instead of awstrack.me.
  • End-to-end HTTPS (no mixed-content errors).
  • Isolation of our reputation from other SES customers.

How?

  1. Verify a sub-domain in SES (e.g., click.example.com).
  2. Point a CDN (commonly CloudFront) at r.<region>.awstrack.me and attach an ACM certificate.
  3. In the configuration set, select “Use a custom redirect domain” and choose the verified domain.
  4. From 30 September 2024, enforce HTTPS for opens and clicks via the new HTTPS-policy option.

Recently, our security team approached me with a critical task: scan all EC2 instances across all AWS accounts to identify servers with the Airlock agent installed and report their versions. What started as a simple request evolved into a robust, modular solution that now supports multiple agent types.

The journey began with these challenges:

  1. Multi-account complexity: Dozens of AWS accounts with different configurations
  2. OS diversity: Windows, Linux (RedHat, Ubuntu, Amazon Linux) with different package managers
  3. SSM requirements: Only instances with online SSM agents could be queried
  4. Output needs: Comprehensive reporting with instance details and agent status

I initially thought shell scripting with AWS CLI would suffice, but quickly hit limitations in error handling, output management, and cross-platform support. This led to the creation of our first Python solution (check_all_accounts_airlock_status.py).

Key Features of the Initial Solution:

  • AWS Profile Discovery: Automatically finds all configured AWS profiles from ~/.aws/config.
  • Multi-account Processing: Handles all accounts sequentially with proper error handling.
  • Smart OS Detection: Identifies Windows vs Linux systems through SSM.
  • Adaptive Command Execution: Runs appropriate commands for each OS type (PowerShell vs Bash).
  • Comprehensive Reporting: Outputs to CSV with all relevant instance and agent details.

The Modular Breakthrough

After delivering the Airlock scanner, I realized we'd need similar solutions for other agents (Dynatrace, New Relic, etc.). This led to the modular redesign (modu.py).

Architectural Improvements:

  1. Abstract Base Class: Created AgentChecker to define a standard interface.
  2. Concrete Implementations: Built AirlockChecker and DynatraceChecker.
  3. Dynamic Output: CSV headers adapt based on agent type.
  4. CLI Flexibility: Choose agents via command line arguments.
from abc import ABC, abstractmethod

class AgentChecker(ABC):
    """Abstract base class for agent checkers"""
    @abstractmethod
    def get_agent_name(self): pass
    
    @abstractmethod
    def get_linux_check_script(self): pass

class DynatraceChecker(AgentChecker):
    def get_linux_check_script(self):
        return """#!/bin/bash
        if [ -d "/opt/dynatrace/oneagent" ]; then
            AGENT_STATUS="Installed"
            # ... version checking logic ...
        fi
        """

Key Achievements

  1. From Specific to Generic: Transformed a single-purpose script into a flexible framework.
  2. Production-Ready Features: Configurable timeouts, retries, and comprehensive error handling.
  3. Time Savings: Reduced a manual, days-long process to minutes.
  4. Future-Proof Design: New agents can be added with minimal code.

Next Steps

  1. Parallel Processing: Scan accounts concurrently for faster results.
  2. Additional Agents: Support for New Relic, Datadog, etc.

  4. Remediation Features: Option to install missing agents.

This project demonstrates how real-world challenges can lead to robust, reusable solutions. The security team got their Airlock report, the monitoring team can now get Dynatrace insights, and we've built a tool that will save countless hours for future agent audits.

The Shift from Reserved Instances to Savings Plans

In recent months, a significant shift in AWS EC2 pricing models has become apparent, particularly concerning the newer EC2 instance families. Instance types like trn2, p5e, i8g, and others have moved away from offering Reserved Instance (RI) pricing. Instead, these families now offer only Savings Plan discount rates. This change prompted a deeper look into the evolving pricing structures and the reasons behind this transition.

Why This Shift is Important

For a long time, Reserved Instances (RIs) were considered the key to unlocking significant savings on EC2 instances, by committing to a set level of usage for one or three years. However, over time, AWS introduced Savings Plans as a more flexible and simplified way to secure similar discounts, without the requirement to commit to specific instance types or regions. This transition represents a larger trend towards simplifying cost management and providing more flexibility to users.

Although Reserved Instances are still available for many legacy instance families, it’s clear that the future is moving towards Savings Plans, which offer a broader and more adaptable approach.

New EC2 Instance Families Affected

Upon reviewing the EC2 pricing models in my AWS region, I noticed that several new instance types, including:

  • trn2
  • p5e
  • i8g
  • f2
  • i7ie

... no longer offer Reserved Instance pricing at all. Instead, the only option listed is the Savings Plan discount structure. This change aligns with AWS's broader trend of simplifying pricing models and offering more flexibility to customers.

A Reflection on the "Convertible RI Double Irish with a Twist"

Previously, some businesses had found creative ways to utilize Reserved Instances, like the well-known strategy dubbed the "Convertible RI Double Irish with a Twist." This approach involved purchasing smaller Reserved Instances with minimal upfront commitment, then converting them into much larger instances as workload demands fluctuated. While this approach had its merits, with the shift to Savings Plans, this type of flexible RI use will no longer be available for newer instance families.

This marks a pivotal change for those who relied on such tactics, as the move to Savings Plans removes the ability to “transform” small instances into larger ones without resetting the commitment period. It’s an interesting evolution of AWS’s pricing structure, reflecting the increasing move towards simplification and predictability.

Impact of This Shift on AWS Users

For those who have already adopted Savings Plans, this shift might not come as a surprise. It reinforces a pattern that’s been emerging for a while. The simplicity and flexibility of Savings Plans have made them a more attractive option, especially when compared to the management complexities associated with Reserved Instances. It’s likely that, over time, more users will see the value in this shift, even if it initially feels like a departure from previous practices.

For businesses that have relied on Reserved Instances for more flexible strategies—such as the Convertible RI Double Irish method—this change will require a shift in cost-management strategies. As Reserved Instances are phased out for newer EC2 instance types, adapting to Savings Plans will become essential for continued savings and effective resource management.

Benefits of Savings Plans Over Reserved Instances

While transitioning to Savings Plans may feel like a new challenge, they offer several advantages over Reserved Instances. Some key benefits include:

  • Equivalent discounts to Reserved Instances, without the need for commitment to specific instance families or regions.
  • Greater flexibility to adjust instance types and families without resetting the commitment period.
  • Automated recommendations that simplify the cost-optimization process, reducing the potential for manual errors.

From a management perspective, Savings Plans are easier to handle compared to Reserved Instances. The process of buying and managing Reserved Instances often involves multiple commitments and limitations. In contrast, Savings Plans offer a more straightforward way to ensure ongoing cost savings with minimal administrative overhead.

Looking Beyond EC2: AWS Services Still Using Reserved Instances

While EC2 is moving towards Savings Plans, other AWS services, such as RDS, OpenSearch, and Redshift, still rely on their own Reserved Instances. Ideally, AWS could consolidate these into a single Savings Plan model, offering customers the flexibility to make usage-based decisions without being locked into specific service architectures due to pricing models.

In particular, services like SageMaker still require users to make architectural choices based on pricing, creating an opportunity for AWS to simplify its approach further. On the other hand, services like Lambda and Fargate have already integrated their discount structures into the Compute Savings Plans, which shows how effective a unified approach can be.

The Future of AWS Pricing Models: A Look Ahead

Looking forward, the move to Savings Plans is ultimately a win for customers. While it may not be necessary to change strategies immediately, it’s worth paying attention to how this shift will shape AWS pricing models in the future. As newer instance types phase out Reserved Instances, Savings Plans are likely to be the primary method for securing long-term discounts across the platform.

What’s encouraging about this change is the gradual phase-out of Reserved Instances. Rather than implementing a sudden cut-off, AWS is allowing businesses to adjust in a way that minimizes disruption, which aligns with the broader trend of making pricing more predictable and manageable.

Conclusion: Adapting to Savings Plans

The simplification of AWS’s pricing models with the introduction of Savings Plans is a clear direction towards a more flexible and user-friendly approach. Moving away from Reserved Instances for newer instance types makes sense, especially for users who have been frustrated by the complexities of managing multiple commitments.

For those who haven’t yet switched to Savings Plans, it’s an opportunity to consider how this new model might benefit future cost optimization strategies. The future of AWS pricing is rooted in flexibility and simplicity—two core principles that Savings Plans embrace fully.
