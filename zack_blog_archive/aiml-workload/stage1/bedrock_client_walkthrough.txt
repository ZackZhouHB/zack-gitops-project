## Section 4: Usage Dataclass

python
@dataclass
class Usage:
    input_tokens: int
    output_tokens: int
    model: Model
    latency_ms: float

    @property
    def cost_usd(self) -> float:
        p = PRICING[self.model]
        return (self.input_tokens * p["input"] + self.output_tokens * p["output"]) / 1000


Why a dataclass:
- Groups related data together
- @property computes cost on-demand (not stored, always fresh)
- Can be serialized to JSON for logging/monitoring

Real-world use: Every LLM call returns a Usage object. You can:
- Log to CloudWatch
- Store in DynamoDB for billing
- Aggregate for dashboards

## Section 6: invoke() Method

python
def invoke(self, prompt: str, model: Model = Model.HAIKU, max_tokens: int = 1024, use_guardrail: bool = False):
    body = {
        "anthropic_version": "bedrock-2023-05-31",
        "max_tokens": max_tokens,
        "messages": [{"role": "user", "content": prompt}]
    }


The request body structure:
- anthropic_version - Required by Claude models, specifies API version
- max_tokens - Limit output length (controls cost + prevents runaway responses)
- messages - Chat format with roles (user, assistant, system)

Why messages format (not just a string):
- Supports multi-turn conversations
- Can include system prompts
- Industry standard (OpenAI, Anthropic, etc. all use this)

## Section 7: invoke_stream() Method

python
def invoke_stream(self, prompt: str, model: Model = Model.SONNET, max_tokens: int = 1024) -> Generator[str, None, Usage]:
    response = self.client.invoke_model_with_response_stream(...)

    for event in response["body"]:
        chunk = json.loads(event["chunk"]["bytes"])
        if chunk["type"] == "content_block_delta":
            yield chunk["delta"]["text"]  # <-- This is the magic


Why yield (Generator pattern):

python
# WITHOUT streaming - wait for entire response
response = client.invoke(prompt)  # 5 second wait
print(response)  # All at once

# WITH streaming - process as it arrives
for chunk in client.invoke_stream(prompt):
    print(chunk, end="")  # Prints word by word


The event types from Bedrock:
- message_start - Contains input token count
- content_block_delta - Contains actual text chunks
- message_delta - Contains output token count (at end)

Real-world architecture:
Browser ←WebSocket← API Gateway ←← Lambda ←← Bedrock (streaming)
         chunks flow back in real-time

## Section 8: smart_route() Method

python
def smart_route(self, prompt: str, max_tokens: int = 1024):
    simple_keywords = ["summarize", "translate", "list", "extract", "yes or no"]
    is_simple = len(prompt) < 500 or any(kw in prompt.lower() for kw in simple_keywords)
    model = Model.HAIKU if is_simple else Model.SONNET
    return self.invoke(prompt, model=model, max_tokens=max_tokens)


Why route between models:

| Query Type | Model | Cost |
|------------|-------|------|
| "Translate hello to French" | Haiku | $0.0005 |
| "Design a distributed system for..." | Sonnet | $0.006 |

This is a simple heuristic. Production systems use:
- ML classifier to detect task complexity
- User tier (free users → Haiku, premium → Sonnet)
- Fallback chains (try Haiku, if bad response → retry Sonnet)

## Section 10: RateLimiter Class (Production Feature)

```python
class RateLimitExceeded(Exception):
    """Raised when user exceeds their rate limit."""
    pass


class RateLimiter:
    def __init__(self, requests_per_minute: int = 60):
        self.rpm = requests_per_minute
        self.buckets: dict[str, list[float]] = defaultdict(list)
    
    def check(self, user_id: str) -> bool:
        now = time.time()
        minute_ago = now - 60
        
        # Remove timestamps older than 1 minute
        self.buckets[user_id] = [ts for ts in self.buckets[user_id] if ts > minute_ago]
        
        if len(self.buckets[user_id]) >= self.rpm:
            raise RateLimitExceeded(f"User '{user_id}' exceeded {self.rpm} requests/minute")
        
        self.buckets[user_id].append(now)
        return True
```

### Why Rate Limiting?

The Problem:
```
Normal user: 10 queries/day      → $0.06
Buggy script: 10,000 queries/hr  → $600 (oops!)
Malicious user: infinite loop    → bankruptcy
```

The Solution:
```
User makes request 1-60  → ✅ Allowed
User makes request 61    → ❌ RateLimitExceeded
User waits 1 minute      → ✅ Allowed again
```

### How Token Bucket Works

```
Time 0:00  - User A requests → bucket: [0:00]           → Allowed (1/60)
Time 0:01  - User A requests → bucket: [0:00, 0:01]     → Allowed (2/60)
...
Time 0:30  - User A requests → bucket: [0:00...0:30]    → Allowed (31/60)
...
Time 0:59  - User A requests → bucket: [0:00...0:59]    → Allowed (60/60)
Time 0:59  - User A requests → bucket is FULL           → ❌ BLOCKED
Time 1:01  - User A requests → bucket: [0:01...1:01]    → Allowed (0:00 expired)
```

### Real-World Use Cases

| Scenario | Rate Limit |
|----------|------------|
| Free tier users | 10 rpm |
| Pro tier users | 100 rpm |
| Enterprise API keys | 1000 rpm |
| Internal services | No limit (trusted) |

### Why defaultdict?

```python
# Without defaultdict - need to check if key exists
if user_id not in self.buckets:
    self.buckets[user_id] = []
self.buckets[user_id].append(timestamp)

# With defaultdict - automatically creates empty list
self.buckets[user_id].append(timestamp)  # Just works
```

## Section 11: invoke_with_retry() Method (Production Feature)

```python
def invoke_with_retry(
    self,
    prompt: str,
    model: Model = Model.HAIKU,
    max_tokens: int = 1024,
    max_retries: int = 3,
    base_delay: float = 1.0
) -> tuple[str, Usage]:
    retryable_errors = ["ThrottlingException", "ServiceUnavailableException"]
    
    for attempt in range(max_retries):
        try:
            return self.invoke(prompt, model, max_tokens)
        
        except ClientError as e:
            error_code = e.response.get("Error", {}).get("Code", "")
            
            if error_code not in retryable_errors:
                raise  # Don't retry auth errors, bad requests, etc.
            
            if attempt == max_retries - 1:
                raise  # Final attempt, give up
            
            # Exponential backoff with jitter
            delay = base_delay * (2 ** attempt)
            jitter = random.uniform(0, delay * 0.1)
            time.sleep(delay + jitter)
```

### Why Retry Logic?

The Problem - Without Retry:
```
Request 1: ✅ Success
Request 2: ✅ Success
Request 3: ❌ ThrottlingException → APP CRASHES
```

The Problem - With Naive Retry:
```python
while True:
    try:
        response = client.invoke(...)
        break
    except:
        continue  # Immediately retry → makes throttling WORSE
```

The Solution - Exponential Backoff:
```
Attempt 1: ❌ Failed  → Wait 1 second
Attempt 2: ❌ Failed  → Wait 2 seconds
Attempt 3: ❌ Failed  → Wait 4 seconds
Attempt 4: ✅ Success!
```

### Why Exponential (not Linear)?

Linear backoff (1s, 2s, 3s, 4s):
- Still hammers the API frequently
- Slow to back off when system is overloaded

Exponential backoff (1s, 2s, 4s, 8s):
- Quickly reduces pressure on overloaded system
- Gives system time to recover
- Industry standard (AWS, Google, etc. all recommend this)

### Why Jitter?

The "Thundering Herd" Problem:
```
Time 0:00 - 100 requests all fail (throttled)
Time 0:01 - 100 requests all retry at exactly 1 second → ALL FAIL AGAIN
Time 0:03 - 100 requests all retry at exactly 2 seconds → ALL FAIL AGAIN
```

With Jitter (random 0-10% added):
```
Time 0:00 - 100 requests all fail
Time 0:01 - Request 1 retries at 1.03s
Time 0:01 - Request 2 retries at 0.98s
Time 0:01 - Request 3 retries at 1.07s
...spread out, system can handle it
```

### Which Errors to Retry?

| Error | Retry? | Why |
|-------|--------|-----|
| ThrottlingException | ✅ Yes | Temporary, will succeed later |
| ServiceUnavailableException | ✅ Yes | Temporary outage |
| ValidationException | ❌ No | Bad request, won't fix itself |
| AccessDeniedException | ❌ No | Auth problem, need to fix code |
| ModelNotReadyException | ✅ Yes | Model warming up |

### Real-World Configuration

```python
# Development - fail fast, see errors quickly
invoke_with_retry(prompt, max_retries=2, base_delay=0.5)

# Production - be patient, maximize success rate
invoke_with_retry(prompt, max_retries=5, base_delay=1.0)

# Batch processing - very patient, running overnight anyway
invoke_with_retry(prompt, max_retries=10, base_delay=2.0)
```

## Section 12: invoke_for_user() Method

```python
def invoke_for_user(
    self,
    prompt: str,
    user_id: str,
    model: Model = Model.HAIKU,
    max_tokens: int = 1024
) -> tuple[str, Usage]:
    self.rate_limiter.check(user_id)  # Raises if exceeded
    return self.invoke(prompt, model, max_tokens)
```

### Why a Separate Method?

This combines rate limiting with invocation for multi-tenant apps:

```python
# Single-tenant (internal tool) - no rate limiting needed
response = client.invoke(prompt)

# Multi-tenant (SaaS product) - must rate limit per user
response = client.invoke_for_user(prompt, user_id="customer_123")
```

## Interview Questions These Features Prepare You For

Q: "How do you handle API throttling in production?"
A: "Exponential backoff with jitter. Start at 1 second, double each retry, add 
   random jitter to prevent thundering herd. Only retry transient errors like 
   ThrottlingException, not auth or validation errors."

Q: "How do you prevent a single user from burning your LLM budget?"
A: "Token bucket rate limiting per user. Track request timestamps, reject if 
   exceeds limit. Different limits for different tiers - free users get 10 rpm, 
   enterprise gets 1000 rpm."

Q: "What's the thundering herd problem?"
A: "When many requests fail simultaneously and all retry at the same time, 
   overwhelming the system again. Solved by adding random jitter to retry delays."

Q: "Why exponential backoff instead of linear?"
A: "Exponential backs off faster when system is overloaded, giving it time to 
   recover. Linear (1s, 2s, 3s) still hammers the system too frequently."
